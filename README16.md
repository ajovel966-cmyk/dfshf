# CSV交付字段怎么用：Excel 一打开就乱码、手机号变 1.55501E+11 的六个坑，附字段表与导入规范

上周三下午，同事把刚下单的压缩包解到桌面，双击那张 `tg_20250821.csv`——屏幕上是一屏问号。手机号那列成了 `1.55501E+11`，邮箱列开头挂着 `ï»¿`，密码列有几行干脆显示 `#NAME?`。他判断是买到了废号，转头去问客服，客服回得很干脆：文件是 UTF-8 编码，你双击用 Excel 打开，它按本地 ANSI 去解，当然乱。

我把同一个文件拖进编辑器看了一眼：字段整整齐齐，一个字符都没丢。问题全在"打开方式"，不在"数据"。

所以这篇只讲一件事——**CSV 交付的字段到底怎么用**。表头每个字段是什么意思、怎么把它无损搬进表格、脚本怎么读它。批量买号真正吃掉时间的从来不是单价，是这一层。

## 这张表是给程序吃的，不是给人看的

在 [TG小号批发](https://www.bignoz.com) 这条线上，10 个起批、6.9 元一个的那款，交付方式是"整包 CSV 账号密码表，带邮箱"。也就是说你付款后拿到的不是一个网页链接让你一个个抄，而是一个文件：一行一个号，一行一个密码。库存显示 999+、已售 48.6k，属于走量的款，走量的东西必然按"能被机器读"的方式组织。

## 字段表：交付三列 + 自建四列

站方交付的表头，通常是这三列（中英文表头都有，先看第一行再动手）：

| 列名 | 样例 | 类型 | 不处理会怎样 | 处理方式 |
| --- | --- | --- | --- | --- |
| `phone` | `+15550123456` | 文本，必填 | 前导 `+` 被吃掉；12 位以上被转成 `1.55501E+11`；超过 15 位末位直接归零 | 导入时把整列设成文本，保留 E.164 格式 |
| `password` | `Kq7#vLm2x` | 文本，必填 | 以 `=` 或 `-` 开头时被 Excel 当公式，单元格显示 `#NAME?` | 别在 Excel 里编辑密码列；要改就前置半角单引号 |
| `email` | `tg0821_001@…` | 文本，必填 | 无 BOM 的文件被按 ANSI 解，整列乱码；有 BOM 时开头三个字节 `ï»¿` 混进表头 | 用 `utf-8-sig` 读，或按 65001 编码导入 |
| `batch` | `20250821-A` | 自建，建议加 | 三个月后出问题，分不清是哪个批次串了 | 下单当天就写进文件名和这一列 |
| `group` | `TH-拉群` | 自建，建议加 | 拉群号、内容号、备用号混在一张表里，替补时找不到人 | 按用途切三组，别按数量切 |
| `status` | `ok` / `pending` / `dead` | 自建，建议加 | 登录结果不落表，返工全靠回忆 | 脚本跑完自动回写，一行一状态 |
| `note` | `首登换过一次` | 自建，建议加 | 30 天质保期内换过号，没人记得换的是哪一行 | 换号当天补一行备注，附订单号 |

前三个字段是资产本身，后四个是管理信息。只盯着前三列、把后四列留到"以后再说"，一批 50 个号跑到第二周就没人说得清谁是谁。

## 乱码与科学计数法：Excel 的默认解码在坑你

Excel 双击打开 CSV 时干了两件"自作主张"的事，两件都能把数据毁掉。

**第一件是按本地代码页解码。** UTF-8 的中文和特殊符号在 GBK 视角下就是一堆问号。表现是整列乱码，或者文件开头多出 `ï»¿` 三个字符——那是 BOM 被当成了正文。

**第二件是猜测数据类型。** 它看到一列全是数字，就按"数字"存：12 位以上转科学计数法，超过 15 位有效数字的部分一律抹成 0。手机号带国际区号普遍 12–15 位，正好踩在线上。更隐蔽的是前导 `+`：它被当成"正号"运算掉，你复制出去给程序用，Telegram 那边直接报号码无效。

还有一个坑只在密码列出现：以 `=` 开头的字符串会被当公式执行，单元格显示 `#NAME?`。你以为是密码错了，其实是 Excel 在算一道不存在的公式。

顺带一个常被误判的弹窗：文件里有内容超长或引号不配对时，Excel 会提示"我们发现 xxx.csv 中的某些内容有问题。是否希望我们尝试尽可能恢复？"——点"是"它会自作聪明地截断。这种情况别点恢复，直接用导入向导。

## 导入规范：六步把 CSV 无损搬进表格

正确姿势是走导入向导，不要双击。Excel 里的路径是：**数据 → 获取数据 → 从文件 → 从文本/CSV**。

1. **先备份原文件。** 交付的 CSV 复制一份到 `raw/` 目录，只读不改，后面所有清洗都在副本上做。
2. **选编码 65001。** 导入窗口的"文件原始格式"选 `65001: Unicode (UTF-8)`。预览里中文和 `@` 正常显示，说明选对了；还是乱码就试 `936: 简体中文 (GB2312)`，别在两种之间反复猜——看预览。
3. **分隔符锁定逗号。** 邮箱和密码里可能带逗号，带逗号的字段在 CSV 里会被双引号包住，这一步别手动改分隔符。
4. **把号码列类型改成"文本"。** 这是最关键的一步，在导入预览里点中该列，类型从"常规"改成"文本"，再点"加载"。改完这一列长什么样就是什么样，不会再变科学计数法。
5. **落地后立刻做三项检查。** 行数（去掉表头）等于下单数量；`phone` 列去重后条数不变；`email` 列空值数为 0。三项有一项不对，先别登录，拿订单号找客服——30 天质保的口径是"首登异常免费换号"，号码本身残缺属于交付问题，越早提越省事。
6. **另存为 xlsx 并锁住格式。** 存成 `.xlsx`，并把号码列的单元格格式固定为文本，之后每次打开都不会被重算。

## 脚本解析：从 `csv` 模块到并发登录的骨架

到 200 个号以上，Excel 就不是工具了，是障碍。脚本读这张表只有三个要点。

**一是编码。** Python 里用 `open(path, encoding='utf-8-sig')`，`utf-8-sig` 会顺手吃掉 BOM；用 `utf-8` 读带 BOM 的文件，第一行表头会变成 `\ufeffphone`，然后你的 `row['phone']` 全程 KeyError。

**二是别让任何一层把号码当数字。** `csv` 模块读出来本来就是字符串，危险的是中间环节：写回 Excel、过一遍 JSON 再转、或者被某个库自动推断类型。整条链路里号码只以字符串存在，校验用正则 `^\+?[1-9]\d{6,14}$`，长度对不上直接进 `invalid` 队列，不要试图"修一下"。

**三是并发要克制。** 小号是独立 IP 注册的，但你 50 个号从一条线路同一分钟挤进去，独立 IP 就白瞎了。我的骨架是：分片读取 → 每片不超过 5 个并发 → 单号之间随机间隔 30–90 秒 → 失败重试两次并指数退避 → 结果逐行回写 `status` 列。跑的过程中随时能停，停了从 `pending` 续跑，不用从头来。

回写这一步值得单独说。脚本跑完必须产出一份新表，而不是只在终端刷日志——日志会滚掉，表格不会。半个月后要给客服报"这 6 个号首登失败"，能拿出来的就是那张带 `status` 和 `note` 的表。

## 三种落地方式怎么选

| 方式 | 适合规模 | 字段怎么过 | 主要风险 |
| --- | --- | --- | --- |
| Excel 导入向导 | 10–50 个 | 手动设文本列，肉眼核对 | 保存时被重算，号码列悄悄变科学计数法 |
| 表格软件 + 脚本混用 | 50–200 个 | 脚本读 CSV，结果回写 xlsx | 中间转存一次就丢精度 |
| 全脚本 / 接口拉取 | 200 个以上 | 字段直接进数据库，全程字符串 | 凭证写死在代码里；循环下单失控 |

第三条路适合长期补号：找客服开通批量权限拿凭证，按数量下单，按订单号拉交付内容，拉回来的字段和 CSV 表头是同一套，脚本不用写两版。要注意的是凭证别硬编码，下单接口要有幂等键——同一个请求重发两次，你收到的是两批号，钱也扣两次。
