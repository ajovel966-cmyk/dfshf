# potato传文件卡在99%？同一个1.8GB安装包传了5遍之后，我摸清了4类大小限制和断点续传的成立条件

上周三晚上十点半，我蹲在客户办公室给一台老工作站装设计软件。安装包 1.83GB，拷U盘嫌麻烦，想着用 potato 直接传过去更快。进度条爬到 87% 就不动了，等了四十多秒，界面下方浮出一行灰字：「发送失败，请重试」。换成手机热点重发，停在 62%；第三次我改了文件名、把压缩包从预览列表里移出去再传，卡在 91%；第四次用手机端发，走到 100% 转了半天圈，结果还是失败。第五遍我干脆不动它，去接了杯水——回来仍是那句一模一样的提示。

结论很朴素：这种反复失败，八成不是"网不好"三个字能打发的。它要么是一头撞上了体积上限，要么是中断之后根本没有接着传的余地，要么是这个文件压根不该走聊天通道。客户端各平台入口和逐项检查清单可以在 [potato使用指南站的下载与排查目录](https://www.belajardroid.com) 里对着看，下面只讲传输这一段。

## 一、先分清三种"失败"：现象像，病因不一样

同一个「发送失败」，那晚我遇到四种版本。先搞清自己属于哪一种，比反复重发有用得多。

| 界面表现 | 实际发生了什么 | 断点续传能不能救 | 先动哪里 |
| --- | --- | --- | --- |
| 进度条停在某个百分比不动，几十秒后提示失败 | 连接被中途掐断：切了网络、锁屏、电脑进睡眠 | 能，但必须在原来那条会话里重发同一个文件 | 保持同一设备、同一会话，别换群 |
| 进度条走满 100% 再转圈，才报失败 | 数据送上去了，服务端落盘或校验没通过 | 基本救不回来，等于要重传 | 换小体积包，或直接走替代路径 |
| 一点"发送"就立刻报错，压根没有进度 | 超过单次上限，客户端在本地就把你拦了 | 不涉及续传 | 看第二节的限制表 |
| 对方收到了，但打不开或显示 0 字节 | 传过去的是云盘占位文件或桌面快捷方式 | 不涉及 | 传实体文件，别传 `.lnk` |

第二行那种最坑人。看着像成功了，其实前面百分之百都白跑。判断办法是盯住"进度条停在多少"：**每次都停在同一位置，说明问题出在文件本身或体积上，跟你家宽带没关系**；每次停的位置都不一样，才是网络在抖。

## 二、四类限制：卡人的往往不是你以为的那一条

默认只有"单文件最大多少G"一条限制，实际卡住人的是四类。

| 限制维度 | 客户端的表现 | 最容易撞上的场景 | 处理方向 |
| --- | --- | --- | --- |
| 单文件体积 | 超限直接拒发，或传到中途无声断掉 | 系统安装包、设计素材、录屏原片 | 分卷压缩，或改用链接 |
| 单次批量 | 一次拖二十几个文件，只有一部分成功 | 手机相册整段导出、一整个素材文件夹 | 分批发，一次十到二十个 |
| 网络与后台状态 | 蜂窝网络下大文件被系统掐断，手机锁屏后任务消失 | 通勤路上发素材、边充边传 | 连 Wi-Fi，把应用加入后台白名单 |
| 本地磁盘与缓存 | 弹「存储空间不足，无法接收文件」 | 长期不清缓存、手机只剩几百兆 | 清缓存，但别把"文件"一起勾掉 |

体积那一栏我不给死数字：不同版本、不同平台的上限并不一致，客户端会在发送前自己拦——**要记的是这个动作：文件拖进聊天窗口后先看有没有缩略卡片和预计体积**。有卡片再点发送，说明本地这关过了；连卡片都不给就是本地判定超限，重试一百次也没用。

## 三、断点续传不是"随时能接"，它要凑齐四个条件

很多人以为只要网络恢复，进度就会自己往前走。它更接近"在原位接着补"，条件缺一条就退化成从头再来。

1. **原来那条消息记录还在。** 断掉之后不要在别的群、别的会话里重发，也不要把失败的那条记录删掉。就地重发同一个文件，才有机会命中续传。
2. **两端版本别差太远。** 桌面端进「设置 → 关于 → 检查更新」，先把版本拉齐。版本跨度大的时候，续传常常表现为"看着在传，实际进度归零"。
3. **传输期间别让它睡。** Windows 打开「设置 → 系统 → 电源和电池 → 屏幕和睡眠」，把"使用电池时"的睡眠临时改成"从不"；macOS 在终端跑一条 `caffeinate -dimsu`，传完按 `Ctrl + C` 结束。手机端同理，把锁屏时间调长，并且别切到别的应用后台。
4. **网络别在 Wi-Fi 和蜂窝之间来回跳。** 一跳就换出口，续传的会话链基本就断了。

四条凑齐，1GB 上下的包通常能一次走完；凑不齐就是我那一晚的循环：87%、62%、91%，每次都以为快好了。

## 四、桌面端的排查顺序：按这个次序点，别乱试

处理顺序比试错次数重要。现在的固定流程是这样，一步没用再走下一步：

1. 进「设置 → 数据与存储 → 缓存管理」，点清理缓存。**只清缓存，不要勾"文件"**，那一栏是已经收到的文件本体，清掉就真没了。
2. 同一个页面里找自动下载相关的开关，把"仅 Wi-Fi"之类的限制临时放开，避免它在移动网络下偷偷中止任务。
3. 进「设置 → 关于」检查更新，装完重启客户端，别只关窗口。
4. 把聊天窗口拉到最底，重新拖入文件。桌面端拖拽比点按钮稳，**如果用剪贴板发截图，先按 `Win + Shift + S` 截好，再回聊天窗口按 `Ctrl + V`**，这样不会带上一堆临时文件。
5. 发送后观察停在第几秒、第几个百分比。停在同一点就别再重试了，直接进第五节。

桌面端和手机端同时往一个群里发大文件会互抢上行带宽，进度条都难看，一次只让一台设备发。

## 五、三条替代路径：把"传不过去"变成"不用传"

判断标准：**单文件超过 1GB、或者已经被它坑过两次以上，就别再跟聊天通道较劲。**

**路径一：网盘或对象存储发链接。** 上传到常用网盘，生成带提取码的分享链接，聊天里只发链接和一行说明。稳、可续，对方断了还能重新下；缺点是对方得登录或装客户端。

**路径二：同一个局域网下直传。** 两边都连着公司 Wi-Fi 时最快。在文件所在目录开一个临时服务：`python -m http.server 8000`，对方浏览器访问 `http://你的IP:8000` 直接点下载，传完 `Ctrl + C` 关掉。不经过任何服务器，速度只取决于路由器。

**路径三：分卷压缩。** 适合必须走聊天通道、又确实超限的情况。用 7-Zip 切成若干份：

```
7z a -v500m 安装包.7z 安装包.exe
```

会得到 `安装包.7z.001`、`.002`……全部发给对方，放进同一个文件夹，只需对第一个执行：

```
7z x 安装包.7z.001
```

后面的自动接上。Mac 上没装 7-Zip 就用系统自带的 `split -b 500m 安装包.exe 安装包.part.`，合并 `cat 安装包.part.* > 安装包.exe`。

## 六、传完别急着说"好了"：两个校验动作

分卷传完、链接发完，最容易出的岔子是"文件到了但内容坏了"，尤其安装包，坏一个字节就在收尾那一步报错，你还以为是软件有问题。所以补两个动作。

Windows 上算一次哈希，和发送方对一下：

```
certutil -hashfile 安装包.exe SHA256
```

PowerShell 里等价写法是 `Get-FileHash 安装包.exe -Algorithm SHA256`；macOS 用 `shasum -a 256 安装包.exe`。两串一致就是完整；不一致只重传那一卷，不用整包重来。

第二个动作是**把校验值一起发过去**：文件名、体积、SHA256 前十六位，对方落地后自己对一遍。群里来回转文件时这习惯省掉一堆"我这边打不开"。

## 七、对方是手机：换个思路，别让他解压

手机端处理分卷基本是自找麻烦——文件管理器不认 `.001`，第三方解压工具又常把中文名弄乱。接收方只有手机时把方案换掉：**发链接，再补一个纯文本说明文件**，写清地址、提取码、装完要开的权限。手机上真正会撞的是存储空间，缓存堆久了只剩几百兆，接收时直接弹「存储空间不足，无法接收文件」，让他先进设置清一遍缓存再重试，比你在那边反复重发有效。

这事说到底三层：确认是不是体积撞墙，确认中断能不能续，两样都不成立就换通道。把这三层理顺，那个 1.83GB 的安装包后来我只用了四分钟就送到对方机器上——走的是局域网直传，聊天里只留了一句"装好了回我"。各平台客户端的获取入口和按场景整理的排查步骤，[potato使用指南站的故障排查栏目](https://www.belajardroid.com) 里按"下载、登录、文件、通话"分了类，对着自己卡住的那一步找就行。
